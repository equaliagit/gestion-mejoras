Laravel para quien viene de Java

Qué es cada carpeta del proyecto, qué hace cada archivo que hemos escrito y en qué se parece —y en qué no— a lo que ya sabes. Escrito para leerse de arriba abajo una vez y volver a él a trozos.

Lo primero

La idea general

Laravel es a PHP lo que Spring Boot es a Java: un armazón que ya trae resueltos el enrutado, el acceso a base de datos, la seguridad, los correos y las tareas programadas, para que tú escribas solo lo tuyo. Si has tocado Spring, el 70% de los conceptos ya los tienes; cambian los nombres.

La diferencia grande, y conviene entenderla desde el principio: PHP no se compila. No hay un .jar ni un .war que generar y desplegar. Guardas el archivo, recargas el navegador y ya está corriendo el código nuevo. Eso hace el día a día muy ágil, y también explica por qué desplegar es simplemente copiar archivos al servidor.

La segunda diferencia: cada petición web empieza de cero. En Java tienes un proceso vivo con su memoria y sus beans en marcha entre peticiones. En PHP, cada vez que alguien pulsa un enlace se arranca la aplicación, se responde y se apaga. Por eso todo lo que tiene que persistir vive en la base de datos o en la sesión, nunca en una variable estática.

Sintaxis

Seis cosas de PHP que chocan al principio

  • 01Las variables llevan $. $user, $proposal. Siempre, también los parámetros. Los nombres de clases y funciones no lo llevan.
  • 02La flecha en vez del punto. Donde en Java escribes user.getName(), aquí es $user->name. Y para lo estático, dos puntos dobles: Proposal::count() es como Proposal.count().
  • 03El punto concatena texto. 'Hola '.$nombre es lo que en Java sería "Hola " + nombre. El + aquí solo suma números.
  • 04Un array es las dos cosas. Sirve de List y de Map a la vez: ['a', 'b'] o ['clave' => 'valor']. Es la estructura que se usa para casi todo.
  • 05El tipado es opcional, pero lo usamos. PHP te deja no declarar tipos; en este proyecto los declaramos siempre (public function view(User $user): bool). Cuesta lo mismo y el editor te ayuda mucho más.
  • 06?-> evita el NullPointerException. $proposal->status?->hasCode(...) devuelve null en vez de reventar si status está vacío. Es el Optional del pobre, pero muy cómodo.

Sobre las clases sin new. Verás cosas como Proposal::where('area_id', 3)->get() sin instanciar nada. Es azúcar de Laravel: la llamada estática crea por dentro un constructor de consultas y te lo devuelve. Piensa en ello como el CriteriaBuilder de JPA, pero legible.

El proyecto

Qué hay en cada carpeta

app/ — tu código. Lo único que escribirás casi siempre Models/ las entidades: Proposal, User, Comment… Enums/ los conjuntos cerrados: Visibility, Priority Policies/ quién puede hacer qué Support/ clases de apoyo nuestras (Permissions) Http/ controladores. Todavía vacío bootstrap/ — el arranque. No se toca config/ — configuración que no cambia entre máquinas database/ migrations/ el historial de la base de datos seeders/ datos iniciales (áreas, estados, roles) public/ — LA ÚNICA carpeta que ve internet. Aquí apunta el dominio resources/views/ — las plantillas Blade. Aún vacío routes/web.php — qué URL lleva a qué código storage/ — logs, caché, archivos subidos. Se escribe sola tests/ — las pruebas vendor/ — las librerías. NO se toca y NO se sube al repositorio .env — contraseñas y ajustes de ESTA máquina. NUNCA se sube artisan — el comando de consola del proyecto

La carpeta public/ es la clave de seguridad del despliegue. Es la única que queda expuesta a internet; todo lo demás —tu código, el .env con las contraseñas, las librerías— queda por encima y es inalcanzable desde el navegador. Por eso insistí tanto en que Plesk pudiera apuntar el dominio ahí dentro y no a la raíz del proyecto.

El código de hoy

Archivo por archivo

Las migraciones — database/migrations/

Son Flyway, exactamente. Cada archivo describe un cambio en la base de datos, se ejecutan en orden por su fecha en el nombre, y Laravel apunta en una tabla cuáles ya pasó para no repetirlas.

Un detalle que en Java no existe: cada migración tiene up() y down(). La primera aplica el cambio, la segunda lo deshace. Sirve para poder retroceder si algo sale mal.

Schema::create('areas', function (Blueprint $table) {
    $table->id();                              // clave primaria autonumérica
    $table->string('name', 80);                // VARCHAR(80) NOT NULL
    $table->boolean('is_active')->default(true);
    $table->timestamps();                      // created_at y updated_at
});

Eso genera el CREATE TABLE por ti, con la sintaxis correcta para MySQL o para SQLite, que es justo por lo que las pruebas pueden correr contra una base de datos en memoria mientras la aplicación de verdad usa MySQL.

Los modelos — app/Models/

Equivalen a las @Entity, pero no declaran el mapeo. La clase Proposal sabe que su tabla es proposals porque Laravel pluraliza el nombre, y sabe que title es una columna porque la lee de la tabla. No hay que escribir un campo por cada columna.

Lo que sí escribimos es lo que la convención no puede adivinar:

  • $fillableQué campos se pueden rellenar de golpe desde un formulario. Es una defensa: si alguien manipula el formulario y envía status_id, se ignora, porque no está en la lista. Por eso las pruebas fallaron al principio y tuve que usar forceFill — el propio mecanismo funcionando.
  • casts()Cómo convertir cada columna al salir de la base de datos. 'decided_at' => 'date' hace que ese campo llegue como objeto fecha y no como texto. Es el @Temporal de JPA.
  • RelacionesLos @ManyToOne y compañía. belongsTo es «yo tengo la clave ajena», hasMany es «los otros tienen la mía», belongsToMany es tabla intermedia. Luego escribes $proposal->area->name y la consulta se hace sola.
  • scope*Consultas con nombre. scopeOpen() se usa como Proposal::open()->get(). Son los @Query de Spring Data, pero encadenables entre sí.

Los enumerados — app/Enums/

Visibility y Priority son enum de verdad, casi idénticos a los de Java: valores cerrados con métodos dentro. La ventaja frente a andar comparando textos sueltos es que el editor te autocompleta y un error de escritura no compila.

$proposal->visibility === Visibility::Anonymous   // comparación segura
$proposal->visibility->label()                    // «Anónima», para pintar

Y como el modelo lo declara en casts(), la conversión entre el texto 'anonymous' que hay en MySQL y el enumerado la hace Laravel sola en los dos sentidos.

El filtro de visibilidad — app/Models/Scopes/VisibilityScope.php

Esta es la pieza más importante del día, y no tiene equivalente directo cómodo en Java. Es un trozo de WHERE que Laravel añade automáticamente a toda consulta que se haga sobre propuestas, en cualquier parte de la aplicación, ahora y dentro de dos años.

Se engancha con una sola línea encima de la clase del modelo:

#[ScopedBy([VisibilityScope::class])]
class Proposal extends Model

Eso de #[...] es una anotación, igual que las de Java, solo que en PHP se llaman atributos y se escriben con almohadilla y corchetes.

El efecto práctico: si dentro de seis meses alguien escribe una pantalla nueva y se olvida por completo de comprobar permisos, la pantalla igualmente no enseñará propuestas privadas, porque el filtro ya está puesto por debajo. La seguridad no depende de que nadie se despiste. Para saltárselo hay que escribirlo a propósito y bien visible:

Proposal::withoutGlobalScope(VisibilityScope::class)  // solo informes y tareas

La política — app/Policies/ProposalPolicy.php

Si el filtro decide qué propuestas aparecen, la política decide qué se puede hacer con una que ya tienes delante. Son las dos caras y hacen falta las dos: sin política, alguien podría adivinar la URL de una propuesta concreta.

Cada método responde sí o no a una acción, y Laravel los encuentra solo por el nombre de la clase (Proposal → ProposalPolicy). Se usa así:

$user->can('decide', $proposal)   // ¿puede aprobar o rechazar esta?

Que es, en la práctica, un @PreAuthorize de Spring Security pero escrito en PHP normal y corriente, sin lenguaje de expresiones raro dentro de una cadena de texto.

Los permisos — app/Support/Permissions.php

Una clase con diez constantes y un método que dice qué permisos tiene cada rol. No es de Laravel, la escribí yo, y existe por una razón concreta: que los permisos estén escritos una sola vez en todo el proyecto. El seeder los crea leyendo de aquí y el código los comprueba leyendo de aquí, así que no puede haber discrepancias entre lo que la base de datos cree y lo que el código cree.

Los seeders — database/seeders/

Rellenan la base de datos con los datos que la aplicación necesita para funcionar: las áreas, los estados, los roles. No son datos de prueba, son datos de arranque, y por eso están escritos para poder ejecutarse mil veces sin duplicar nada (updateOrInsert, findOrCreate). En el servidor se lanzarán una vez el día del despliegue.

Las pruebas — tests/Feature/

PHPUnit, hermano directo de JUnit: una clase, métodos que empiezan por test_, aserciones dentro. Dos diferencias con lo que conoces:

La primera, use RefreshDatabase; hace que cada prueba arranque con una base de datos limpia y recién migrada, en memoria, y se tire al terminar. No hay que preparar nada ni limpiar después.

La segunda, $this->actingAs($usuario) simula que esa persona ha iniciado sesión. Eso es lo que hace que las pruebas de visibilidad sean de verdad: no comprobamos el filtro por dentro, comprobamos que un empleado concreto contando propuestas obtiene el número correcto.

Por qué escribí pruebas precisamente de esto. Un fallo de visibilidad no se ve: la aplicación funciona igual de bien enseñando una propuesta privada de más. No hay pantalla roja ni excepción. La única forma de enterarse es que alguien lo descubra, y para entonces ya ha pasado. Doce pruebas automáticas son el único aviso que vamos a tener, y se ejecutan enteras en segundo y medio con php artisan test.

Comandos del día a día

ComandoQué hace
php artisan serveLevanta la aplicación en localhost:8000. Ctrl+C para pararla.
php artisan testEjecuta todas las pruebas.
php artisan migrateAplica las migraciones que falten.
php artisan migrate:fresh --seedBorra todo y reconstruye la base de datos desde cero. En local, cuando algo se ensucia.
php artisan db:seedVuelve a sembrar catálogos y roles.
php artisan tinkerConsola interactiva contra la aplicación viva. Como el jshell, pero con acceso a todos tus modelos.
php artisan route:listTodas las URL que responde la aplicación.
vendor/bin/pintFormatea el código al estilo estándar. Como el formateador del IDE, pero igual para todos.
composer require nombre/paqueteAñade una librería.

Si algo se comporta raro después de un cambio de configuración, casi siempre es la caché: php artisan optimize:clear la vacía entera. Es el equivalente a limpiar el target/ antes de recompilar, y en el servidor será uno de los pasos del despliegue.
